# セーフティとバージョン管理・自動停止ルール

## 1. プロジェクト立ち上げ時の初動必須タスク（Git初期化）
- プロジェクト開始直後、いかなる実装コードの作成よりも前に、必ず `.git` の初期化（`git init`）が完了しているか確認すること。
- 未初期化の場合は直ちに初期化を行い、テンプレート初期状態をファーストコミット（例: `feat: initial scaffold commit`）として記録すること。

## 2. こまめなセーブ（Micro Commit）の原則
- **セーブ地点としてのコミット**:
  - 実装作業中、機能追加やバグ修正が1ステップ完了するごと（または5ファイル変更・重要ロジック変更前）に、必ずGitコミットを打つこと。
  - 「まとめて最後にコミットする」のではなく、作業中の巻き戻しポイント（セーブ地点）として機能単位でこまめにコミットを作成すること。
- **コミットメッセージの明確化**:
  - 「何を変更したか」「なぜ変更したか」を明瞭に記録すること（Conventional Commits形式を推奨：`feat:`, `fix:`, `refactor:`, `docs:`, `test:` 等）。
  - 一度に大量の変更を溜め込んでまとめてコミットすることは厳禁とする。

## 3. セマンティックバージョニング（Git Tag）規約
- **タグ運用の目的**:
  - 通常の作業コミットとは区別し、リリースや大きな開発マイルストーン達成時のみ、SemVer（`vX.Y.Z`）に基づくGitタグ（Annotated Tag）を付与すること。
  - コマンド例: `git tag -a vX.Y.Z -m "リリース/マイルストーン概要"`
- **バージョニング基準**:
  - `X`（メジャー）: 後方互換性のないUI/アーキテクチャの全面刷新
  - `Y`（マイナー）: 互換性を維持した新機能の追加
  - `Z`（パッチ）: 不具合修正や微調整のみ
- **繰り上がりルール**:
  - 左の桁が繰り上がった場合、右の桁は `0` にリセットすること（例: `v0.1.3` ➔ `v0.2.0`、`v0.2.5` ➔ `v1.0.0`）。

## 4. 自動停止（ブレーキ）基準とコミット連動
人間が熱中して指示を連続している場合でも、以下の条件に該当した場合は作業を一旦停止し、確認を求めること：
- 連続して5ファイル以上の新規作成または変更を実施したとき。
- 大きなタスク（マイルストーン）が1つ完了したとき。
- **停止時の必須アクション**:
  1. `.context/00_handover.md` を最新状態に更新する。
  2. その状態を必ず Git にコミットする。
  3. 「区切りに達したため引き継ぎスナップショットを更新し、Gitコミットを完了しました。内容を確認し、次の方針を指示してください」と報告する。

## 5. 破壊的変更の禁止
- 既存の関数・クラスの削除、広範囲のリファクタリング、ライブラリのバージョン変更を行う際は、必ず「変更理由」と「影響範囲」を提示し、ユーザーの承認を得ること。

## 6. 推測による補完の禁止
- 要件に曖昧さがある場合やエラーの原因が特定できない場合、推測でコードを書き進めてはならない。必ず立ち止まり、ログの提示を求めるか質問を行うこと。
