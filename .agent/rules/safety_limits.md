# セーフティとバージョン管理・自動停止ルール

## 1. プロジェクト立ち上げ時の初動必須タスク（Git初期化）
- プロジェクト開始直後、いかなる実装コードの作成よりも前に、必ず `.git` の初期化（`git init`）が完了しているか確認すること。
- 未初期化の場合は直ちに初期化を行い、テンプレート初期状態をファーストコミット（例: `feat: initial scaffold commit`）として記録すること。

## 2. 小さなマイルストーンごとの確実なGitコミット義務
- 「1つの機能の追加」「エラーの解決」「リファクタリングの完了」など、小さく区切ったマイルストーンを達成するたびに、必ず自律的または人間に促して Git コミットを実行すること。
- コミットメッセージには「何を変更したか」「なぜ変更したか」を明瞭に記録すること（Conventional Commits形式を推奨：`feat:`, `fix:`, `refactor:`, `docs:`, `test:` 等）。
- 一度に大量の変更を溜め込んでまとめてコミットすることは厳禁とする。

## 3. 自動停止（ブレーキ）基準とコミット連動
人間が熱中して指示を連続している場合でも、以下の条件に該当した場合は作業を一旦停止し、確認を求めること：
- 連続して5ファイル以上の新規作成または変更を実施したとき。
- 大きなタスク（マイルストーン）が1つ完了したとき。
- **停止時の必須アクション**:
  1. `.context/00_handover.md` を最新状態に更新する。
  2. その状態を必ず Git にコミットする。
  3. 「区切りに達したため引き継ぎスナップショットを更新し、Gitコミットを完了しました。内容を確認し、次の方針を指示してください」と報告する。

## 4. 破壊的変更の禁止
- 既存の関数・クラスの削除、広範囲のリファクタリング、ライブラリのバージョン変更を行う際は、必ず「変更理由」と「影響範囲」を提示し、ユーザーの承認を得ること。

## 5. 推測による補完の禁止
- 要件に曖昧さがある場合やエラーの原因が特定できない場合、推測でコードを書き進めてはならない。必ず立ち止まり、ログの提示を求めるか質問を行うこと。
