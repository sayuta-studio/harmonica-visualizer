# アーキテクチャ・設計パターンの知見（Gotchas）

> **記録指針**: 抽象的な設計論ではなく、「デッドロックの回避、設定ファイルの安全な読み書き、例外処理の共通パターン」など実戦的な知見を記録してください。

## 蓄積された知見

### 1. Python関数内インライン `import` による `UnboundLocalError`
- **落とし穴 (Gotcha)**:
  - モジュール先頭で `import foo` していても、ある関数内の「後方」で `import foo` や `foo = ...` が存在すると、Pythonコンパイラはその関数スコープ全体で `foo` をローカル変数（`STORE_FAST` / `LOAD_FAST`）として認識する。
  - その結果、関数前半で `foo.bar()` を呼び出した時点で `UnboundLocalError: cannot access local variable 'foo' where it is not associated with a value` が発生する。
- **回避策・ベストプラクティス**:
  - **関数内インライン `import` の原則禁止**。すべてのモジュールインポートはファイル最上部（モジュールレベル）に集約する。

### 2. リアルタイム処理とオフライン合成（バッチ処理）の計算ロジック二重管理破綻
- **落とし穴 (Gotcha)**:
  - プレビュー/リアルタイム再生側と、ファイル出力（動画レンダリングやWAV合成等）側で、時間軸補正・オフセット計算（`offset_ms` 等）を別々の関数にハードコードすると、片方の符号反転（`+` と `-` の取り違え）や端数処理の差で必ず同期ズレ・不整合が生じる。
- **回避策・ベストプラクティス**:
  - 時間軸・オフセット計算は単一の基準計算式（例: $t_{\text{src}} = t_{\text{song}} - \Delta t_{\text{offset}}$）に統一し、プレビュー・オフライン合成の双方が同一の関数・モジュールを参照する構造にする。

### 3. 設定管理の粒度分離（全体設定 vs ドメインコンテキスト設定）
- **落とし穴 (Gotcha)**:
  - すべての設定値を1つの `settings.json` に混在させると、対象ファイルやデータ固有のコンテキスト（特定曲の移調量、変え指設定、ループ区間等）と、アプリ全体の設定（音量、テーマ、入出力デバイス等）が衝突し、別ファイルを開いた際に意図しない上書きや状態破壊が発生する。
- **回避策・ベストプラクティス**:
  - **グローバル設定**（`user_settings.json`）: アプリ全体共通設定（UIテーマ、オーディオデバイス、共通デフォルト値）。
  - **個別コンテキスト設定**（`<ファイル識別名>_profile.json`）: ドメイン固有設定（トラック割り当て、オフセット、個別編集状態）。対象ロード時に自動復元・保存する。

### 4. 動画・レンダリング出力におけるアスペクト比と真のフレームバッファ解像度
- **落とし穴 (Gotcha)**:
  - 画面プレビュー用の固定アスペクト比（例: 16:9）の描画ロジックに引きずられ、縦型（9:16）や 4:3 の動画出力をする際に横長画面の中央に黒帯（ピラーボックス）を付けた状態でエンコーダ（FFmpeg等）に渡してしまう。結果として無駄な黒帯が焼き込まれ、字幕やUIがはみ出す。
- **回避策・ベストプラクティス**:
  - 出力先の真のアスペクト比に応じたフレームバッファサイズ（9:16なら `1080x1920` 等）を動的に算出し、エンコーダに直接その解像度を指定して全域レンダリングを行う。テキストや装飾の描画座標もレンダリング幅に対する相対比率で計算する。

### 5. プロジェクトのディレクトリ世代管理・アーカイブ運用・成果物肥大化防止
- **落とし穴 (Gotcha)**:
  - 開発が進むにつれ、初期プロトタイプ（`0.01`, `bbbbb` 等）や過去バージョン（`v2.0`, `v2.1`）がルート直下に散乱し、AIや開発者が「どこが現行本番コードか」を誤認しやすくなる。
  - 過去フォルダ内に過去のテスト書き出し動画（`.mp4`）や中間生成物が蓄積し、プロジェクト全体で数GB単位の無駄な容量圧迫が発生する（本プロジェクトでも過去のテスト動画だけで約2GBを占有していた）。
  - 開発手法のパラダイムシフト（例: メモ帳での手動コピー時代 ➔ VS Code/Git/AI駆動環境時代）の境界が曖昧になり、過去資産を参照する際の認知コストが増大する。
- **回避策・ベストプラクティス**:
  - **「トップ階層は最新バージョンのみ常駐」原則**:
    - ルート直下には常に最新本番コード（現行: `v3.0/`）のみを露出させ、直接アクセスを担保する。新メジャーバージョン（`v4.0`）に移行した際は、旧バージョンを `archives/` へ退避する「世代交代型スライド運用」を採用する。
  - **「開発環境・世代ごとのアーカイブ階層分離」**:
    - 単に過去版を1箇所に固めるのではなく、開発環境の分水嶺（例: メモ帳コピー時代の `archives/v0_v1_notepad_prototypes/` と、VS Code環境以降の `archives/v2.0/`, `v2.1/`）で階層を分けることで、設計思想の違いを明確にする。
  - **「ソースコード完全保持 ＆ 生成メディア（output）の選択的除去」**:
    - 過去の知見が詰まったソースコード（`.py` や設定）は1バイトも消さずに隔離保護しつつ、容量の大半を占めるテスト書き出し動画（各バージョンの `output/*.mp4` 等）のみを特定して除去することで、知見を損なわずにギガバイト単位の軽量化を実現する。
  - **配布物領域の標準化（`releases/`）**:
    - 日本語フォルダ名（`公開ファイル` 等）はコンソールや外部ツールで文字化け（`Jt@C` 等）を引き起こすため、世界標準の `releases/` に統一して配布用ZIP・展開パッケージを集中管理する。

### 6. 【重要・ルール候補】存在しない外部実体の「推測によるコード・設定補完（捏造）」の厳禁
- **落とし穴 (Gotcha)**:
  - 外部のマスターテンプレート（`..\00_template` 等）や親ディレクトリ、別リポジトリから「ファイルをコピーして適用せよ」と指示された際、ワークスペース外に対象が存在しない（またはアクセス権がない）場合、AIが「文脈から推測して、それっぽいコードやバッチファイルを自律生成して配置してしまう」という危険な振る舞い（Hallucinated Substitution）をする。
  - その結果、公式マスターの実装（安全性チェック、例外処理、更新対象のスコープ）と微妙に異なるファイルが混入し、マスターテンプレートと各プロジェクト間で**知見やスクリプトのサイレントドリフト（不整合・乖離）**を引き起こす。
- **回避策・ベストプラクティス（行動原則）**:
  1. **存在しない外部実体の推測補完を厳禁とする**:
     指示された外部ファイルやフォルダが見つからない、またはアクセス境界外である場合は、勝手に類推してコードを生成・配置してはならない。直ちに作業を停止し、「指定パスに対象が存在しません。中身を提示していただくか、配置してください」と人間に報告・停止しなければならない。
  2. **セキュリティ・スコープ境界の即時開示**:
     ワークスペース外のファイルアクセスが遮断された事実、あるいは探索結果（パスが存在しなかった事実）を隠蔽・曖昧にせず、即座に人間にフィードバックする。
  3. **マスター同期物の純度維持**:
     テンプレートから配布される共通スクリプト・ルールは「1バイトの差異も許されないマスター同期物」として扱い、AIが自律的・部分的に書き換えることを禁止する。

### 7. AIモデルの特性・レート制限に応じた分業運用（Architect-Builder パターン）
- **落とし穴 (Gotcha)**:
  - 数千行規模に肥大化したコードベースに対して、高速・軽量モデル（Flash系等）に抽象的な要件定義だけを渡して直接実装させると、既存変数名の取り違え（`AttributeError`）、シグナルブロック漏れ（Signal Storm）、広範囲編集による既存結線の破壊など、コードの乱れが発生しやすい。
  - 一方、高推論モデル（Pro / Ultra系等）ですべての細かい実装・反復テストまで行おうとすると、使用枠（クォータ・レート制限）を急速に消費してしまう。
- **回避策・ベストプラクティス**:
  - **フェーズ1（Architect：上位推論モデルによる設計・マイクロ指示書化）**:
    - 上位モデルでコードベース全体を俯瞰・精査し、変更対象のファイル名、正確な行番号、関数シグネチャ、完全なデータ辞書定義、および1回あたり50〜100行以内で完結する **「マイクロステップ実装指示書」** を `.context/02_tasks.md`（および基本設計は `.context/01_architecture.md`）に直接書き出してコミットする。
    - `.context/` 直下に一時的な番号ファイル（`04_...` 等）を乱立させず、標準の `02_tasks.md` にチェックリスト一体型として統合することで、テンプレート構造の純度を維持する。
  - **フェーズ2（Builder：高速モデルによる1ステップ実装 ＆ Micro Commit）**:
    - 同じチャット欄で高速モデルに切り替え、`02_tasks.md` の Micro-Step を1つずつ順番に実行させる。
    - 1ステップ完了ごとに構文チェック（`py_compile` 等）と Git コミット（Micro Commit）を必須とし、高速モデルが自身の推測で設計変更を行う余地をゼロにする。

### 8. タスク粒度の2層構造化（Micro Commit × Batch Execution による認知負荷低減）
- **落とし穴 (Gotcha)**:
  - AIの迷走を防ぐためにタスクを極小（Micro-Step）に細分化することは安全面で極めて有効だが、1関数・1ステップごとに毎回チャットで人間に確認・承認を求めると、開発者が「確認疲れ・マイクロマネジメント疲れ」に陥り開発テンポが著しく低下する。
- **回避策・ベストプラクティス**:
  - **内部実行層（Git/AI）**: 変更の独立性・安全なロールバック性を担保するため、コード修正は必ず「1ステップ＝1コミット（Micro Commit）」の原則を厳守する。
  - **対話インターフェース層（人間/AI）**: 密接に関連する 2〜3 個の Micro-Step を **「1つの実行パッケージ（Batch Package）」** として上位設計（Architectフェーズ）段階でグルーピングする。
  - 高速モデル（3.8等）には「パッケージ内のステップを1つずつ順番にコミットしながら自動連続実行し、パッケージ単位で人間に短報する」運用を指示することで、**コードの堅牢性（Micro Commit）と開発者の快適性・高テンポを両立**させる。

### 9. コードソース汚染防止とポータブル基底パス解決規約（開発環境 vs 配布EXE）
- **落とし穴 (Gotcha)**:
  - Python GUI / デスクトップアプリで、ユーザーデータ（録音WAV、出力動画、プロジェクト設定等）を保存・生成する際、安易に `BASE_DIR = os.path.dirname(os.path.abspath(__file__))` を基底パスとして使用すると、開発中のテスト実行（`python src/main.py`）時に `src/` 配下に動的フォルダ（`projects/`, `recordings/` 等）が勝手に作られ、ソースコード領域が汚染されてしまう。
  - さらに、これを防止しようと安易に相対パス `projects/...` を直書きすると、PyInstaller 等で EXE 化（配布パッケージ化）した際に実行パスが狂い、保存先が行方不明になる不具合が発生する。
- **回避策・ベストプラクティス**:
  1. **2層ベースディレクトリ解決関数（`get_base_dir`）の唯一化**:
     - `config.py` 等で一元管理し、実行環境に応じて「真のルート」を自動解決する：
       ```python
       def get_base_dir() -> str:
           if getattr(sys, "frozen", False):
               # 配布EXE実行時 ➔ exeと同じ階層（ポータブル展開）
               return os.path.dirname(os.path.abspath(sys.executable))
           else:
               # 開発時 (.py直接実行) ➔ srcの親（プロジェクトルート）
               src_dir = os.path.dirname(os.path.abspath(__file__))
               return os.path.dirname(src_dir)
       ```
  2. **ソースコード領域（`src/`）の不可侵維持**:
     - 開発時、生成データは必ず `src/` の外（プロジェクトルート直下の `projects/`, `recordings/`, `output/` 等）に生成させ、`src/` 配下を100%「純粋なプログラムと付属固定リソースのみ」に保つ。
  3. **`.gitignore` によるルート遮断**:
     - プロジェクトルートに生成される動的データフォルダは `.gitignore` に `/projects/`, `/recordings/`, `/output/`, `/temp/` を明記し、Gitリポジトリを永続的にクリーンに保つ。

### 10. 【重要・ルール化】実装計画書における「表題・要約のみの手抜き指示」の禁止と、行番号・具体的コードスニペット完備の義務化
- **落とし穴 (Gotcha)**:
  - 上位推論モデル（Architect: Gemini 4.0等）に「実装計画書・指示書を作成せよ」と指示した際、AIがトークンや手間を惜しんで「Step 1: ○○を修正する」「Step 2: △△のUIを追加する」といった**表題・箇条書きの要約だけ**を `.context/02_tasks.md` に書いて満足してしまう現象が発生する。
  - この「表題だけの不完全な指示書」のまま軽量・高速モデル（Builder: Gemini 3.8等）に引き継ぐと、Builder側が数千行のコードから自力で該当箇所を探し、変数名やロジックを「推測・発明」して実装することになり、スコープ外エラーや既存結線の破壊、UIレイアウト崩れが再発する（Architect-Builder分業の意義が失われる）。
- **回避策・ベストプラクティス（絶対遵守ルール）**:
  1. **「表題・方針のみ」のマイクロステップ作成を厳禁とする**:
     - Architectが `.context/02_tasks.md` に実装計画・Micro-Stepを策定する際は、各ステップに必ず以下の3要素を完備しなければならない：
       - **① 対象ファイルと正確な行番号・関数名**（例: `src/main.py` の `_apply_visual_dict_to_ui_and_gl` L2796〜2876付近）
       - **② そのまま組み込み・置換可能な具体的Pythonコードスニペット**（シグナルブロック `blockSignals`、クラス定義、辞書キーまで完全に記述されたコード案）
       - **③ 指定のGitコミットメッセージ**
  2. **`02_tasks.md`（詳細仕様書）と `00_handover.md`（進行管理テーブル）の同時更新義務**:
     - `02_tasks.md` に詳細コード仕様を書くと同時に、必ず `.context/00_handover.md` にも全パッケージ・全ステップの進行管理テーブル（解決課題・概要・ステータス一覧）を記載し、Builderが起動直後に全体像と詳細仕様の双方を100%把握できる状態でバトンを渡すこと。
